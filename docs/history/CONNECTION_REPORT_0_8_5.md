# 0.8.5 手机反馈与后续修正

维护者提供了构建 c053e5252ecfc6a9d6d2b79dcd48ccc611fcd478、API 37、Google-only 的连接报告。报告保留多个进程/旧会话，导出头表示当前安装版本，不能把此前的每条传输直接归属给当前构建。下面按报告原始 UTC 时间分析本次启动段。

- 03:43:57 的 AUTH_OK 后进入目录请求。03:43:59 已有多个 IPv4 的有效 API 401 探测。
- 03:44:00.038 的 CHECK_BEGIN 紧接 ROUTES_RESET。正在进行的选线因 networkEpoch/generation 改变，在 03:44:00.168 返回 SELECT_FAILED，目录随后 LIST_FAILED/IO。源头是 startCheck 在检测开始调用全局 reset，并非这些端点均不可用。
- 两次手动检测随后在约 6.5–6.8 秒完成。API 的匿名 401 和内容根路径 404 分别属于服务探测，不能当作真实文件下载结果。
- 后续目录得到 HTTP 200。03:44:56 缓存连接在约 22ms 发现网络错误，备用地址接替，请求在 1.6 秒左右返回 HTTP 200，回退生效。
- 本次段只出现四个 IPv4/A 加密 DNS 请求，代码在该次收集时没有进入 IPv6 分支；原日志没有记录缺少全局地址、缺少默认路由或平台数据等原因。IPv4 加密 DNS 超时时，系统 DNS 仍提供了候选，随后端点验证成功。

0.8.6 调整：手动检测通过 DirectRoutes.check 实际重验缓存，避免清空全局路线/连接池及使旧请求失效；保留有效备用项，取消及存储失败不把健康路线标为坏。增加 IPv6 状态原因、IPv6 范围数、A/AAAA 候选数及启动版本码；报告头另显示当前平台 VPN/IPv6 状态，明确旧日志可能来自以前版本。
